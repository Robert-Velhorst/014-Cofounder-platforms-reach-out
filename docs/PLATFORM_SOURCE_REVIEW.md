## Catalogue maintenance and review reminders

Each public card shows its public-page review date outside the evidence disclosure.
After **30 UTC calendar days** it displays an editorial review reminder. Invalid,
impossible or future dates display "Review date needs checking" instead of an age.
The browser's device clock supplies the reference date on render; reload/reopen
the view to refresh it, and check a suspect device clock. This is not a background
monitor, availability probe, permission renewal, authenticated acceptance test or
automatic admission/retirement decision. Even a recent review can be obsolete.
Due records remain discoverable and existing source-policy restrictions remain.

Maintainer procedure:

1. Prioritize due/invalid dates and reported changes. Re-read the actual official
   access, pricing, terms, privacy and relevant exact-channel pages. Search snippets
   are leads, not review evidence. Do not sign up, submit forms, inspect member
   profiles or test provider actions without appropriate separate authority.
2. Record the actual review date, exact URLs, relevant observations and unresolved
   conflicts in this source ledger. Amend the record in
   `apps/cofounder-discovery/server/platform-catalogue.ts`. Advance `reviewedAt`
   only after a substantive direct-source review, never merely to clear a reminder.
   Preserve prior dated supplements; do not imply other records were rechecked.
3. If a source is temporarily unreadable, retain the last review date and record
   the failed observation separately. A tool error does not establish closure,
   price, access or changed rules. Hold publication when the available evidence
   cannot support an honest discovery listing: move the record out of the published
   `sources` array into a dated held-entry record in this source ledger, preserving
   its ID, URLs, last substantive review and hold reason (as with F6S). There is no
   per-record publication flag or maintainer UI. Do not delete customer data.
4. Retire/hold a confirmed defunct, duplicate or unsafe listing with dated direct
   evidence and a documented replacement/alias where justified. Keep it internally
   in this internal source ledger for provenance, but exclude it from public discovery. Review source-policy
   handling independently: hiding a card must never allow an unknown or previously
   blocked source into candidate import or outreach. Never treat a re-review or
   provider rebrand as automatic `manual-reviewed` or integration permission.
5. Update current counts in README/gap map, preserving historical checkpoint
   counts. Run catalogue, review-date and source-admission tests, type checks/build,
   and desktop/mobile search/evidence checks. Publication/commit/merge still needs
   authority. Changes to real provider access or permissions require their own
   evidence and acceptance process.

The 30-day window is a product-maintenance convention, not a provider promise or
legal standard. No unattended scheduler or automatic website fetching is enabled.

Maintain a worldwide-oriented, expandable catalogue of discovery routes, with manual assistance as the default. The original September review below contains **27 records**: 7 dedicated matching services, 12 community/channel records, and 8 program/event/ecosystem records. The October supplement above adds five. These are not implemented integrations, and the list is not a finite or exhaustive inventory of every relevant platform worldwide.

Official public pages were opened and reviewed. Signups, memberships, authenticated workflows, purchases, private groups, provider APIs, scraping, and sending were not exercised. Marketing descriptions establish advertised purpose, not independently measured quality, active-member counts, success rates, or end-to-end availability. No personal member records are reproduced here.

The recommended assistance mode is a **product decision**, not a provider's permission grant. Manual participation must still satisfy the provider's terms, channel rules, content restrictions, user authorization, and privacy requirements. A user's approval cannot substitute for required provider permission.

- `M`: manual discovery, user-authored profile/application preparation, and user-reviewed drafts only where current rules allow; the user operates the provider interface and decides whether to submit.
- `H`: human-original participation only; no generated or AI-edited text for posting. Internal discovery notes and reminders may still be useful.
- `G`: permission-controlled channel; first establish the exact group/workspace/server, membership, administrator rules, and allowed purpose. No member harvesting or assumed access.
- `Hold`: record retained for research; do not activate the relevant public-beta capability until the named uncertainty or permission gate is resolved.
- `API unverified`: no approved discovery/outreach API use case was established by this review. This does **not** mean that the provider has no API.
- Pricing `unknown` means no applicable official price was verified. Free signup is not evidence that messaging, premium filters, events, or commercial API use are free.

## Recommended catalogue maintenance contract

The following is an implementation recommendation, not a claim about the current application:

- Store a stable source ID, canonical name/URL, verified aliases, category, audience/regions, access constraints, pricing status/source, assistance mode, automation status, evidence URLs, reviewed date, reviewer, and explicit unresolved questions.
- Keep `listed`, `manual-assistance-available`, `provider-permission-verified`, `integration-implemented`, and `live-integration-verified` as separate states. A checked link changes only link availability.
- Add per-source flags for `requires_membership`, `requires_admin_permission`, `allows_ai_post_drafts`, `public_link_permission_unresolved`, and `pricing_unverified`. Unknown permissions must fail closed.
- Before activating an automated capability, record the exact permitted action, data fields, retention/deletion terms, account scopes, rate limits, commercial authorization, and provider evidence. Obtain user approval for external writes separately.
- Recheck rules and access before use; schedule periodic catalogue review (suggested monthly) and immediate review after redirects, access errors, policy changes, or user reports. This document does not itself create a recurring automation.
- Do not count aliases, generic private-channel classes, unavailable sources, or research-only records as implemented integrations. Display the review date and uncertainty in the user-facing catalogue.
